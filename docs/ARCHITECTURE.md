# Architecture

Playkeeper runs **several game servers on one host**: an authenticated HTTPS web panel, a narrow local control agent on a Unix socket, an isolated Minecraft Java container per server with its own persistent world data, and SQLite for application and event state. The web process does not run as root and never receives the Docker socket. Only the agent performs operations, from an explicit allowlist, and user input is never interpolated into host-shell commands. Game ports are separate from management. No external database, provider VM API or hosted control plane is involved; the one hosted piece is optional, the names service behind free `playkeeper.io` addresses, which manages their DNS records ([services/names](../services/names/README.md)).

All of it is one Go binary with the TypeScript/React UI compiled in; the processes, users and files are described in [decisions/0002-stack.md](decisions/0002-stack.md), and how several servers, the data model and the dashboard fit together in [decisions/0004-playkeeper-2.md](decisions/0004-playkeeper-2.md). The game image is pinned by digest; the server software is a Paper build from PaperMC's version list, checked against the SHA-256 PaperMC publishes for it. Minecraft server software is downloaded from its upstream on the user's server after explicit EULA acceptance; Playkeeper never ships proprietary server binaries.

## Servers, machines and projects

- The panel keeps projects, the machines in them and who may do what; for now there is one project, one machine (the local agent) and one admin. The agent keeps the machine's servers. Every server has a random ten-character id, a name and a URL slug; every per-server row (operations, events, sessions, samples, backups, audit) carries its id.
- A new server gets its own directory (`/var/lib/playkeeper/servers/<id>/`), container (`playkeeper-mc-<id>`), RCON secret and the next free game port. A server migrated from 0.2.0 keeps 0.2.0's container, paths, secret and labels exactly, so its container definition does not change and it keeps running through the upgrade.
- Operations are exclusive per server, so two servers can back up or restart at the same time; a Playkeeper update waits until every server is idle. Each server reserves its memory budget even while stopped, so it can always start.
- The panel routes each request by server to the machine that runs it. Player faces are fetched from Mojang by the panel and cached in its database; browsers never contact Mojang.
- A machine can have one address: a free `<name>.playkeeper.me` from the names service, which points it at the address the machine's signed requests come from, or its own domain, whose records the admin adds. Free names lived under `playkeeper.io` before; the agent moves a name saved under it when it starts, and the service answers installs from before the move with `update_required`. The agent keeps the address and gets and renews its Let's Encrypt certificate (DNS-01 through the names service for a free name, HTTP-01 on port 80 for an own domain), saving it where the panel can read it; the panel serves it for that name and its self-signed certificate for the IP address and anything else. Servers share the machine's name and differ by port; an SRV record per server lets players join at `<server>.<name>` without the port.
- The machine's name opened in a browser shows the public server page (from 0.4.3): each server that's on it (each server's switch, on by default), with its status, version, software, modpack, join address and shared map, and player names only while the owner shows them. The panel can't open ports below 1024, so the agent opens 443 and 80, only when nothing else listens on them, no Docker container publishes or names them, no web server set to start with the machine would take them, and the machine has been up for three minutes, and passes the listening sockets to the panel over its socket (`SCM_RIGHTS`; machine links don't carry that route). A port found busy isn't tried again until the agent restarts or the owner asks. The panel serves only the page there, through a public group of its own (`internal/panel/serverpage.go`), with only the agent's certificate for the name on 443, a redirect to HTTPS on 80 once 443 works, and Let's Encrypt's HTTP-01 checks passed on to the agent, which checks over the loopback address that they reach it before it counts on port 80's holder. It holds the ports while a server is on the page and the machine has an address, and closes them as soon as that stops (`internal/panel/pageports.go`, `internal/agent/pageports.go`). From 0.4.4 the agent also keeps what the owner adds to the page with each server: an About text, a Twitch or YouTube channel, and a status board that the owner's tools post through the API or the `set_status_board` tool, which Playkeeper never fetches from anywhere (`internal/agent/publicblocks.go`). The panel draws the page's share card from the same answer (`internal/sharecard`). From 0.4.4 a server can have its own address under the machine's own domain: the plan gives it A records and an SRV record of its own, the agent gets its HTTP-01 certificate within a daily cap, and the page answers that name with the server alone (`internal/agent/ownaddress.go`).
- Two-factor sign-in lives in the panel: `internal/twofactor` holds the rules (codes, recovery codes, pausing and blocking), and the panel stores each user's factor and runs the second sign-in step.
- The few routes that work without a sign-in are all in the panel's public group (`publicRoutes()` in `internal/panel`), which limits what each address can do and logs only each route's prefix. The friends' pack page, `/packs/<token>` (from 0.4.0), is one: the panel asks its machines which server the token belongs to, and that server's agent answers only while sharing is on and the server is running.

## Pre-generation and packs

- Pre-generating the map drives [Chunky](https://modrinth.com/plugin/chunky), installed as a managed add-on, through the server's console; `internal/pregen` speaks its console language on Paper, Fabric, NeoForge and Forge and reads the task it saves, and Chunky's config is set so a task continues after a restart. The agent keeps the task it started last on each server (the `pregen` table) and checks it every 5 seconds while the server runs: it pauses the task while players are online, continues it once the server has been empty for 2 minutes, and leaves alone a task someone paused. A task finishes when Chunky logs that it finished, as Chunky saves a finished task as cancelled while its last chunks still load; one that Chunky reports as cancelled, or no longer has, for a minute ends as cancelled.
- Data packs live in the world's `datapacks` folder, which the agent writes only inside the server's data folder (`os.OpenRoot`) and as the game's user. They are switched on and off through the running server's console with Minecraft's own `datapack` commands (`minecraft:datapack` on Paper, so plugins can't replace them), and the agent waits until the server reports the change; a stopped server switches a new pack on when it starts.
- Resource packs are kept once per machine, named by their SHA-1, in `/var/lib/playkeeper/resourcepacks`. Offering one sets the server's container environment (the pack's URL and SHA-1), so it applies from the next start. Players' games refuse the panel's self-signed certificate, so the panel's port also answers plain HTTP: `/resource-packs/<sha1>.zip` serves, without a sign-in, only packs a server offers, and every other plain-HTTP request is redirected to HTTPS. The link uses HTTPS instead while the panel serves a publicly trusted certificate for exactly its host, valid for a week more. The agent decides at each start, so a certificate that arrives or lapses changes the link from the next start: a running server keeps the link it started with, and the Packs page says the change applies after a restart.

## Uploaded worlds and the map

- A world upload is up to 16 archives (`.zip`, `.tar.gz` or `.tar`, recognised by their content) that the browser sends in 64 MB pieces through the panel to the agent. The agent keeps what arrives of each file in its staging folder, so after a dropped connection the browser asks where the upload stands and sends the rest. The agent keeps up to 4 open uploads in memory and clears the staging folder when it starts, so an upload doesn't survive a restart; the dashboard deletes its upload when the page is left, reloaded or closed, and when another upload opens or announces a file the agent drops the ones nobody has touched for an hour while they still wait for bytes, or for a day once every byte has arrived.
- `internal/worldimport` reads the archives without unpacking them: it lists the Java Edition worlds inside with their dimensions, including the separate Nether and End folders Paper keeps, reads each `level.dat`, and plans what a server of the chosen type and Minecraft version gets: the folders it writes, what it leaves out and why, the settings it carries over and anything that stops the import. The owner confirms that preview; only then is the world written into the staging folder, each entry checked against what was read before.
- A server made from an upload is created with the staged world moved into its empty data folder, so a failure leaves no server without its world. When its Minecraft version upgrades the world, a verified backup of the world as uploaded is made before the first start. The agent can also replace a server's world the way a restore does, although the dashboard doesn't offer it yet: a verified rollback archive of the current world first, then only the world folders and what the upload brings are swapped in, and swapped back out if the server doesn't start.
- The live map is [squaremap](https://modrinth.com/plugin/squaremap), installed through the add-on library as a plugin on Paper and Purpur or a mod on Fabric, Quilt and NeoForge; it has no Forge build for current Minecraft, so Forge servers have no map. The `maps` table has a server's row from turning the map on until turning it off, with the records of what it installed; the Plugins or Mods tab lists those files as used by the Map and refuses to adopt, update or remove them. The map counts as on only while those files are still in the folder: once one is deleted, the Map tab says so, the shared link stops working, and turning the map on clears what is left and installs squaremap again, unshared. Before every start the agent writes squaremap's config (`internal/webmap`): its web server listens on port 25580 inside the container and is never published, new land is drawn with one thread, and it neither checks for updates nor fetches player heads. After the first start with squaremap, the agent asks it once, through the server's console, to draw the land explored so far.
- squaremap draws only chunks that exist, so a new server's map is little more than spawn. The map's area is the server's latest pre-generation (`internal/agent/maparea.go`): choosing a bigger one on the Map tab starts pre-generating it, in place of one under way, and Explored only cancels one under way; what was generated stays. Up to the world border takes the border's width from the game's `worldborder get` for the estimate, and Chunky's `worldborder` command for where it is when the task starts. squaremap draws new chunks as they are generated, a few hundred every half minute; when a pre-generation finishes while the map is on, the agent asks it for a full render of the overworld, whose progress the Map tab shows.
- The agent is the only hop to squaremap: it reaches it at the container's address on Playkeeper's private network, asks only for the worlds, the players and PNG tiles, and rebuilds the JSON from the fields the map page uses, so squaremap's own page and scripts never reach a browser. The Map tab calls the panel's signed-in routes. The shared map is the dashboard's page at `/map/<link code>` and the calls it makes under `/api/public/map/<link code>/`, served by the panel's public route group (`publicRoutes`), which also serves the resource packs, the names service's liveness check and the friends' pack page: it limits each address, answers anything unknown, switched off or failing with one 404, and logs only the route's prefix. The agent answers them only while the map is on and shared and the server runs with squaremap loaded, and leaves players out unless their switch is on.

## Each server's files

- The Files tab lists, opens, saves, uploads, downloads, makes folders in, moves and deletes a server's data folder, through the agent of the machine that runs it (over its link for a joined machine). The agent does all of it through `internal/gamefiles` (`browse.go`): a path from the dashboard must be relative and without dot segments (`fs.ValidPath`), every folder on the way is checked with Lstat to be a real folder before `os.Root` opens anything, and a handle is checked again once it is open, so a folder swapped for a link in between is refused. A link or special file at the name itself is listed as what it is and never opened; moving or deleting it moves or deletes the link. Files are written to a new temporary file and renamed into place, a name that must be free with `RENAME_NOREPLACE` against checked handles on the folders, and new files and folders are given to the game's user. Each change takes the server's operation lock, shared between changes, so no start, wake, backup or restore begins until it is done; a delete still going after 30 seconds answers that it carries on, and keeps the lock until it finishes. A zip download is counted first (`Dir.Count`) and refused above 100,000 files and folders, which `archive/zip` keeps a header of in memory until it ends, and walks and counts stop 64 folders down; the dashboard asks with `?check=1` before it follows a zip's link, since a link can't show why a download failed.
- While the game runs, the world folders (the level's, and `_nether` and `_the_end` beside it) are read-only, and the agent refuses any change there; when Docker can't say whether the game runs, it counts as running. Other files can change and apply when the server restarts, which the dashboard says. Nothing changes while an operation (a backup, a restore, an update) has the server.
- The editor opens UTF-8 text without NUL bytes up to 2 MB; anything else is only downloaded. A save names the SHA-256 the editor opened and is refused once the file changed, for example when a plugin wrote its settings meanwhile. For `server.properties` the agent names the keys it sets from the server's settings at each start (from the container's environment), which the editor marks.
- Uploads work like world uploads: the browser announces each file with its path in the folder (a dropped folder names the folders it makes) and sends it in 64 MB pieces from the byte the agent has, and the agent keeps what arrives in its staging folder and puts each file in place once it is whole, only as a regular file and over another only when asked. Each agent keeps up to 8 open file uploads of up to 1000 files; what they may still receive counts against the space world uploads may use. A download streams one file as it is, or a zip of folders or of several files from one folder that leaves links and special files out. The panel names and types every download itself (`application/octet-stream`, `Content-Security-Policy: sandbox`), so nothing a machine sends renders as a page of the dashboard, and gives upload pieces a rate limit of their own.
- Only admins see or change a server's files (`files.view`, `files.edit`): the files hold what the dashboard keeps from moderators and viewers (the RCON password in `server.properties`, plugins' tokens and passwords, logs with players' addresses), and a changed or uploaded file can run code in the game. Every change is in the audit log (`files.saved`, `files.created`, `files.uploaded`, `files.folder_made`, `files.renamed`, `files.moved`, `files.deleted`, and `files.downloaded`) and in the recent activity, with uploads into one folder within 15 minutes as one line.
- From 0.4.9 a server can also have a `secrets` folder beside its data folder, for keys its plugins read that nobody sees again: the OpenRouter key the AI Build Battle plugin builds with is `secrets/openrouter_api_key`, the key's bytes with no newline, which the plugin reads again at every build. The folder is the game user's and only theirs to read (0500, each key 0400), and a container mounts it read-only at `/run/playkeeper/secrets` (with `z` where Docker labels containers for SELinux) only while its server has the folder, so no other server's container changes. The agent (`internal/agent/aikeys.go`) makes it empty before each start of a server with the plugin (an add-on record with source `playkeeper` and project `ai-build-battle`) and when a key is saved, and writes a key to a new file that it renames over the old one. Removing a key leaves the folder, so a new key needs no restart; a key saved while the running container lacks the mount is pending until the server's next start. Being outside the data folder, the keys are out of reach of the Files tab, backups and their copies somewhere else, world copies, the Disk space page and the template export, and deleting the server deletes them first. The dashboard only saves or removes a key (`PUT` and `DELETE /api/servers/{id}/ai-keys/{provider}`, with the Files tab's rights) and reads whether each is set and applies yet (`GET /api/servers/{id}/ai-keys`); no answer, log line, audit entry (`ai_key.saved`, `ai_key.removed`, naming the provider) or error carries a key.

## Backups and copies somewhere else

- Each server's backup rules (`internal/backup/retention`) decide when the agent makes a backup and which backups it keeps, here and somewhere else; the agent deletes the rest.
- With copies on, the root agent encrypts each new backup with age in a spool folder of the server's own, uploads it (`internal/offsite`: S3 signed with SigV4, or SFTP with a pinned host key), tries again with backoff when that fails, and records each copy in its database. The panel only forwards requests: it never holds the storage secrets or the keys.
- Getting a copy back downloads, decrypts and checks it into the same staging area as an uploaded backup, so it goes through the same preview and the same restore: the rollback archive, the journaled world swap and its recovery at start. Until the stage is ready it can be cancelled, and it never writes a swap journal, so a cancelled download, or one the agent stopped in, leaves nothing for recovery to act on: the next start records it as interrupted and deletes its files. Restoring on a new machine lists and stages copies with the key file and storage details sent with the request, and saves neither.
- While a restore isn't over (it is running, or its stage still has its swap journal), the backup rules keep its rollback archive, the Disk space page offers nothing of its server, nor the stage, and the World tab discards none of the server's world copies. A journal the agent can't read may be any server's, so it keeps every server's rollback archives and world copies and makes every server busy, and the agent logs it; a readable one whose restore is no longer on record keeps all of its server's rollback archives.

## Invariants

- Preflight existing listeners, services, resources and file paths before changing a host. Never assume ownership of a running Crafty or systemd Minecraft world. Keep an install manifest and a reversible uninstall path that does not destroy user worlds.
- Bootstrap auth locally; HTTPS, CSRF protections, session expiration, rate limiting and administrative authorization on control actions. Neither Docker nor RCON is externally available. Audit privileged actions, not secret values.
- A server's data folder is the game's, and its plugins and mods can put links, named pipes or huge files there. The agent reads and writes files there through `internal/gamefiles`, which refuses them and says which file is in the way.
- Define desired vs observed state and idempotent start/stop/restart, per server. Handle agent disconnect, simultaneous operations, crash and reboot coherently.
- Bound log/event retention. Prefer real player event logs with deduplication and session-gap handling; add a Paper plugin only if observed sources are insufficient. Avoid storing player IPs unless essential and documented.
- A consistent world backup doesn't need a stop: on a running server the agent sends `save-off` and `save-all flush` over RCON, copies the world while saving is paused, then sends `save-on` until the server confirms it. The RCON adapter honours the caller's deadline and never resends a command it has written, so each reply answers the command the backup sent: saving already on at the first `save-on` means something else turned it on during the copy, and that copy is discarded. Saving left paused is recorded per server, shown in the dashboard and retried by the reconciler until the server saves again. A Minecraft version change, a restore and a backup the owner asks to make with the server stopped still stop it gracefully. Record archive manifest/integrity and storage location; a local archive alone must be labelled on-host only. Protect restore with explicit preview, validation and rollback archive. A backup can also be restored as a new server.
- Changes to Playkeeper and to the game version only go forward and can be undone. An installed Playkeeper installs only a newer release signed with a key compiled into it. The sandboxed agent cannot replace its own binary, so it verifies and stages the release, and a root oneshot updater started by a systemd path unit checks it again, swaps the binary and units, restarts only the agent and panel, and puts the previous binary, units, config and databases back if the new version is not healthy. A Minecraft version change backs up the world first and restores it if the new version does not start.
- Every UI string goes through the translation layer (`web/src/i18n`); a test fails on text written straight into a component.
- Keep one tested clean-host install route and one short recovery runbook ([RECOVERY.md](RECOVERY.md)). A packaged release must run outside the developer checkout.
